The Binding Ceremony
Moves to the Intranet

SMS-03 built a ceremony that starts in a Buzz channel and anchors a phone number to a Nostr key. Two things are wrong with that, and the second is the serious one: it presumes Buzz membership, which is a higher-friction door than the phone line it gates, and it anchors the binding to a key the record cannot resolve to a person. This page designs the ceremony as a profile act on the intranet, where a member is already authenticated and already resolvable, and where the binding can be anchored to the identity the record actually holds. It designs one migration and applies nothing.

§2

What is actually wrong today

four findings, each read off the live record on 2026-08-26

One. A binding names a key the record cannot resolve to a person. phone_bindings.member_pubkey is NOT NULL and holds a 64-character hex Nostr pubkey. There is no other column anywhere in the CIS that mentions a pubkey: a search of information_schema.columns for any column matching pubkey or nostr returns exactly that one column and nothing else. So the CIS can say that a number is bound, and cannot say to whom. Every authority question downstream of a binding has to be answered outside the record.

Two. The ceremony presumes the harder door. The ceremony is !bind and !verify in a Buzz channel, which means a member must hold a Nostr key, run or be given a client, and be seated on the hive before they can bind a phone. The phone line was meant to be the lower-friction door. Gating it on the higher-friction one is backwards, and #247 says so.

Three. No member can read their own messages. phone_events has row-level security enabled and exactly one policy, phone_relay_insert from 0027, which permits the relay to append and nothing else. There is no SELECT policy for any role. 0026 wrote that the member-scoped read would arrive with the binding; it has not arrived, and 133 rows of members’ own correspondence currently sit where only the service key can read them. #247 is the moment to fix it and §5 does.

Four, and this one is latent rather than live. anon and authenticated hold every table privilege on both phone_events and phone_bindings, including DELETE, because the Supabase creation defaults were never stripped. 0009 found this on the live apply and wrote the lesson down: strip the defaults first, or the column discipline is decoration. 0026 and 0028 did not strip. Nothing is exposed today only because neither table carries a permissive policy for those roles. This design adds the first one, so the migration strips the defaults before it adds the policy, and grants back column by column.

what was not verified

Whether the two verified bindings on the live record belong to people the record knows is not a thing this page can determine. One of the two keys matches the steward’s owner pubkey as recorded in the relay operator’s local notes; the other is unidentified from inside the estate. Naming either is a human act and it is decision SMS5-D3.

§3

The identity the intranet already holds

verified in the shipped code, not assumed

The ceremony has to attach to whatever the intranet actually does, so this is what it actually does, read out of the deployed source rather than inferred.

  1. The gate sends a magic link. assets/shell.js posts the member’s address to GoTrue at /auth/v1/otp with a redirect_to back to the page that asked. There is no password anywhere and no second factor enrolled.
  2. The session is a Supabase JWT in local storage, under the key sb-ujujwgopdwirebgcpekc-auth-token; assets/shell-gate.js reads it before first paint and marks the document in or out, failing closed.
  3. The record resolves the person server-side. Every policy in the authority map calls app_agent_id(), a security-definer function that reads auth.uid() from the JWT and returns the agents.id whose auth_user_id matches. That function, and not the client, is the identity.
  4. The surface that already edits a member’s own record is the directory’s Edit your profile drawer at /commons/directory/, which finds the signed-in member by auth_user_id and writes their profiles row. That is the natural home for the ceremony control, and choosing it finally is the UI packet’s to make, not this page’s.

So the anchor this design uses is agents.id, reached only through app_agent_id(), never passed in as an argument by a client. That is the same anchor every other member act in the record already uses.

the honest weakness

Magic-link email is not phishing-resistant and it is not a passkey. #191’s comments say plainly that binding is the soft underbelly of the whole phone channel, and that binding and re-binding should eventually be passkey-gated with out-of-band notice. No passkey store exists in this estate today; RESEARCH/cis-as-a-service/SPEC.md §3.6 works out what one would cost. This design is strictly stronger than what it replaces, because a magic-link session resolves to a person the record knows and a Nostr key does not, and it is strictly weaker than where the channel should end up. Both sentences are true and neither should be dropped when this is quoted.

§4

The ceremony, end to end

five steps, and the reason the database cannot do it alone
stepwho actswhat happens
1 · askthe member, signed inEnters a number in E.164 and submits. The page calls phone_bind_request() with the anon key and the member’s bearer token. The verb resolves the actor with app_agent_id(), refuses a non-member, refuses a malformed number, refuses a member who already holds a live binding, refuses a number that already holds one, applies both rate limits, and writes a row with status requested and origin intranet. No code exists yet.
2 · sendthe relayThe poll loop already runs every fifteen seconds on the co-op line. It picks up requested rows under the phone_binder key, mints a six-digit code, stores its SHA-256, sets code_sent_at and code_expires_at, sends the SMS through Quo, and moves the row to pending. A send that fails moves the row to failed and tells the member on the surface.
3 · confirmthe member, still signed inTypes the code back into the same page. phone_bind_confirm() checks that the row is theirs, that it is pending, that the code has not expired, that the attempt budget is intact, and that the digest matches. On a match the row becomes verified, verified_at is set, and the hash is cleared.
4 · recordthe verbsEach of the three verbs writes an events row: phone.binding.requested, .verified, .revoked, carrying the binding id and the origin and never the number. The challenge SMS and its delivery status land in phone_events as carrier traffic already does.
5 · end itthe member, or STOPphone_bind_revoke() from the profile surface, or STOP over the line, which the relay already honours. Either way the row becomes revoked with a reason and a timestamp; nothing is deleted.

Why step 2 is a separate actor, which is the one non-obvious choice here. The database cannot send a text message. Something has to hold the carrier credential, and there are two honest places to put it: a Supabase edge function invoked by the page, which means the Quo key moves into Supabase’s secret store and a second sender exists; or the relay that already holds that key, already talks to Quo, already polls, and already writes phone_events. This design takes the second, so the ceremony adds no new holder of the carrier credential and no new outbound path. The cost is latency: a code arrives within one poll interval rather than instantly, and the surface should say “within a few seconds” rather than pretend otherwise. The election is SMS5-D2.

§5

The migration, and the property that governs it

0029, extending rather than superseding

Preservation is the load-bearing property. Three rows exist on the live record: two verified and one pending. A migration that orphans a verified binding is a defect, not a migration, because an orphaned binding is a member whose phone silently stops working. So 0029 extends phone_bindings rather than replacing it. Every existing row keeps its status, keeps its key, takes origin='buzz' from the column default, and takes a NULL agent_id. phone_router_select reads status='verified' and is untouched, so routing does not change by one row.

There is no backfill, and that is a decision rather than an omission. Nothing in the record maps a Nostr key to an agent (§2, finding one). Guessing which person a key belongs to would be the agent asserting an identity binding, which is precisely the act #247 says belongs to a ceremony. The two legacy rows therefore stay anchored on their keys until a human names them or their holders walk the intranet ceremony. That is SMS5-D3.

changewhat it is for
+ agent_idThe member the intranet authenticated, nullable, referencing agents. Nullable because the legacy rows have none and because forcing one would mean inventing it.
+ originbuzz, intranet, or steward, defaulting to buzz so existing rows are described truthfully rather than relabelled.
+ code_expires_at, code_attempts, code_sent_atExpiry and the attempt budget become row state rather than service state, so a code is dead the moment it is late even if nothing has run.
member_pubkey drops NOT NULLA member who has never touched Buzz has no key to offer, which is the whole complaint in #247.
+ anchor constraintsA row must carry an agent_id or a member_pubkey, and an intranet-origin row must carry an agent_id. A binding anchored to a phone number alone is the credential this whole piece exists to stop trusting.
+ two states, four revoke reasonsrequested for the gap between asking and a code existing; expired and failed for the two ways a ceremony dies without a binding; attempts, send_failed, number_reassigned, rebind as reasons.
+ unique live agentOne live binding per member, partial on status='verified', the same shape 0028 gave the key and the number.

The RLS half. Two policies arrive, and the creation-default grants are stripped before either of them exists.

-- a member reads their own bindings, every state
create policy phone_bindings_self_read on phone_bindings
  for select to authenticated
  using (agent_id = app_agent_id());

-- and their own messages, for exactly the period their binding covered
create policy phone_events_self_read on phone_events
  for select to authenticated
  using (exists (
    select 1 from phone_bindings b
     where b.agent_id = app_agent_id()
       and b.peer_e164 = phone_events.peer_e164
       and b.verified_at is not null
       and phone_events.occurred_at >= b.verified_at
       and phone_events.occurred_at < coalesce(b.revoked_at, now())
  ));

The window is closed at both ends deliberately. Open at the front, a member would read whatever the previous holder of that number said. Open at the back, a member would keep reading a number after they gave it up. Closed at both, a member reads their own correspondence and only their own, and the number can change hands without either party inheriting the other’s record.

Two columns are withheld by grant rather than by policy. code_hash is a SHA-256 of six digits, which is to say it is the code: a member who could read it could finish a ceremony without ever receiving the SMS, and the possession proof would be gone. It is withheld the way profiles.email is, by column privilege. phone_events.payload and .error hold the raw carrier record and operational text, which are the envelope and not the correspondence.

A member holds no INSERT or UPDATE on either table. Every member write travels through one of three security-definer verbs, in the shape apply_for_membership() established in 0007. This is not tidiness: a member who could UPDATE phone_bindings could set their own status to verified.

§6

Revocation, and a number that changes hands

the direction that is never dangerous, and the one that is

Ending a binding is always allowed and always immediate. Three doors: the member clears the number on their profile, which calls phone_bind_revoke(); STOP over the line, which the relay already honours and which carrier rules require; or a steward act. All three write a status, a timestamp, and a reason. Nothing is deleted, the evidence trail stays, and the member keeps their read of the traffic the binding covered.

Taking a live number from its holder is the dangerous direction, and this design does not automate it. A number that has genuinely moved to a new person is a real case and it will happen; recycled mobile numbers are ordinary. But the request to rebind a number that already holds a live binding is indistinguishable, at the surface, from an attacker who has acquired the number. So phone_bind_request() refuses a number that is already bound, with the same answer it would give for any other unavailability, so the verb is not an oracle for who holds what. Resolving a genuine reassignment is a steward act with revoke_reason='number_reassigned', and the controls #191 asked for belong to it: notice to the existing holder’s registered email at the moment of the request, and a delay during which the old binding still receives notices and either party can cancel. Neither the notice nor the delay is built by this piece; both are named here so the gap is visible rather than discovered.

Re-binding your own number to a different one is the easy case: revoke, then request. The unique index permits it the moment the old row is revoked, and the probe walks exactly that path.

§7

Rate limits, expiry, and what is written down

the levers, and where each one lives
levervalue proposedwhere it is enforced
code lifetimeten minutescode_expires_at on the row, checked in the confirm verb. Same figure the Buzz ceremony uses.
attempts per codefive, then the row retirescode_attempts, checked and incremented in the confirm verb.
sends per numberthree per rolling dayThe request verb. This is #247’s open question three, answered as proposed and open to being overturned.
requests per memberfive per rolling dayThe request verb. Not in #247; added because the per-number cap alone lets one member walk a list of numbers.
outbound costone segment per challengeThe relay’s existing GSM-7 fold and segment cap. A challenge is short by construction.

What is logged, and where. Ceremony acts are member acts on the member’s own record, so they go in events: phone.binding.requested, .verified, .revoked, each carrying the binding id and the origin. The number is not in the event payload. It is in the binding row, which is column-guarded and policy-scoped; events is read by members and by officers under existing policies, and a phone number in a payload would be a disclosure nobody asked for. The challenge SMS itself and its delivery status land in phone_events as carrier traffic, exactly as every other message on the line does. A refused request is recorded as a refusal, not as silence, because a member who cannot bind should be able to see why.

What is not logged: the code, in any form, anywhere, once verified; the digest, once the ceremony ends; and the number in any surface a third party reads. The relay’s existing discipline that credentials never appear in logs covers the rest.

§8

The decisions, staged and not taken

three, and the first is the steward’s open question from #247
SMS5-D1 · does the Buzz-originated ceremony survive · the steward

#247 asks it and does not answer it. The choices are three, not two. Retire it: one ceremony, one anchor, and the SMS-03 ceremony code comes out of the relay, at the cost that a member without an intranet session has no path at all. Keep it as a steward-only fallback: the !bind path stays but answers only the owner pubkey, which covers the case of a member who cannot sign in and needs a binding made for them, at the cost of keeping two ceremonies and two anchors alive in one service. Keep it open to members: the status quo, which leaves the weaker anchor available to anyone who prefers it, and which the drafter does not recommend, because an anchor is only as strong as its weakest available ceremony. The migration is written so that any of the three applies without another migration: origin='buzz' stays a legal value and member_pubkey stays a legal anchor. Drafter’s cut, offered and not taken: the middle one, with the fallback’s bindings written as origin='steward' so the record says which hand made them.

SMS5-D2 · who sends the code · the steward, on the builder’s recommendation

The relay, which already holds the Quo credential and already polls, or a Supabase edge function invoked by the page, which is instant but puts the carrier key in a second place. This is an egress and custody question as much as an engineering one: the estate already has one holder of that key on one host, and the doctrine has been to keep the number of holders down. Drafter’s cut: the relay, accepting up to one poll interval of latency and saying so on the surface.

SMS5-D3 · the two legacy bindings · the steward, by name

Two verified bindings anchor on Nostr keys the record cannot resolve. Either a human names the agent behind each key, which is a data act on the live record and needs the same care as any other, or their holders walk the intranet ceremony and the old rows retire with revoke_reason='rebind'. The second is cleaner and slower and is the drafter’s cut. Doing nothing is also viable and is what the migration does by default: the rows keep working, anchored on keys, until someone decides.

Two questions from #247 are answered here rather than staged, because the answer follows from the design rather than from a judgement that is anyone else’s to make. Question two, whether the profile shows the member their own number: yes, and it shows the whole binding, because phone_bindings_self_read serves the member their own row and a member who cannot see what they bound cannot check it. Question three, the rate limit: three per number per day as proposed, plus a per-member cap the issue did not name, for the reason in §7.

§9

How anyone would check this

the battery, and what a green run does not say

scripts/sms05_probe.py stands a scratch Postgres, applies 0001, 0002, and 0026 through 0029, shims auth.uid() to a transaction-local setting the way rls_probe.py does, seeds the two legacy bindings in the shape the live rows carry, and walks the ceremony as a member walks it. It runs in CI as the sms05-ceremony job. Every probe cites the section or the anchor it holds. What it asserts:

  • Preservation, twice: the legacy rows are verified, keyed, unanchored to an agent, and visible to phone_router both before the walk and after it.
  • The anchor constraints refuse a row with neither anchor, and an intranet-origin row with no agent.
  • The ceremony: an applicant is refused, a malformed number is refused, a member gets a request, a wrong code refuses and counts, another member cannot confirm someone else’s ceremony, the right code verifies, and the digest is cleared.
  • The secret: selecting code_hash as the member whose code it is fails on privilege.
  • The reads: a member sees their own binding and not another’s; a member sees the messages inside their window and not the ones before it, after it, or on someone else’s number; payload is refused.
  • No hand on the table: direct INSERT and UPDATE by a member are refused, and one live binding per member holds.
  • Revocation and reassignment: the member revokes their own, the window closes behind them, a second member binds the same number and inherits no history, and the first member loses none.
  • The rate limit refuses the fourth send to a number in a day.
what a green run is silent about

It says nothing about the relay, which this piece does not modify; nothing about the carrier; nothing about the surface, which is a separate UI packet; nothing about whether the migration has been applied to the live CIS, which it has not; and nothing about whether magic-link email is a strong enough factor to bind a phone, which is a judgement and not a test.

§10

What this does not decide

restated so no drift is possible
  • No tier above read. Unchanged from #191 and #240. This is not the second factor, and it must not be quoted as one.
  • No change to the allowlist floor for unbound numbers, and no change to the silent drop.
  • No UI. The form, the code entry, and the revocation control are a separate deliverable under the UI bed, citing this address.
  • No guest standing. #261 waits on this piece for its second defect, the phone number as the whole credential; it is not answered here and it is a wider question than a ceremony.
  • No bus. The 2026-08-23 addendum on #247 proposes custodial keys and an internal message bus. That is a larger piece and the issue itself proposes it as its own address.
  • No passkey. Named as the destination in §3 and built by nobody yet.
